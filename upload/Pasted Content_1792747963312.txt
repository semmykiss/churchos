# CHURCHOS — EXISTING FINANCE MODULE UPGRADE MASTER PROMPT

## 1. ROLE AND OBJECTIVE

Act as a senior enterprise software architect, church financial systems consultant, chartered-accountant-level financial controls specialist, database engineer, and full-stack application developer.

You are working on my existing **ChurchOS church management application**. The application already has a Finance Module and other operational modules.

Your task is to **upgrade and extend the existing Finance Module only** into a comprehensive, secure, professional church financial management system suitable for Nigerian churches, including RCCG-style church structures with local assemblies, areas, zones, provinces, and headquarters where applicable.

This is an enhancement of an existing production application, NOT a request to create a new application or rebuild the entire Finance Module from scratch.

The upgraded module must support accurate church accounting, income collection, expenditure management, fund accounting, budgeting, financial approvals, reconciliation, reporting, and appropriate access for pastors, accountants, treasurers, ushers, departmental leaders, finance committees, auditors, and members.

## 2. ABSOLUTE SCOPE RESTRICTION — FINANCE MODULE ONLY

This requirement takes precedence over all other implementation decisions.

Modify only the existing Finance Module and the minimum supporting backend components, database objects, authorization rules, and shared interfaces strictly necessary to make the Finance Module work correctly.

### Do not modify, rebuild, rename, redesign, remove, or disrupt:

- Authentication and existing login functionality.
- User registration and account management.
- Existing tenant management and tenant provisioning.
- Existing church administration and organizational structure.
- Member management and member profiles.
- Departments and departmental management.
- Attendance management.
- Services and event management.
- Communication, announcements, and notifications outside the scope of Finance integration.
- Existing partner, licensing, or subscription functionality.
- Existing reports belonging to other modules.
- Existing application navigation, shared layouts, global design system, or unrelated dashboards.
- Any other working application module or its business logic.

Do not remove or replace existing Finance Module functionality merely because a new implementation seems preferable.

Preserve existing Finance Module features, records, routes, interfaces, and integrations wherever possible. Enhance them incrementally.

Do not introduce a separate, competing Finance Module.

Do not create a second authentication system, a duplicate member database, a duplicate departmental directory, or an independent church hierarchy.

Reuse existing ChurchOS entities, services, authentication, tenant context, branch structure, UI components, permissions framework, and design conventions where appropriate.

If an existing feature needs modification to support the upgrade, make the smallest backward-compatible change possible.

If a requirement cannot be implemented safely without modifying another module, document the dependency and implement the minimum necessary integration contract. Do not independently redesign or modify that other module.

## 5. ROLE-BASED FINANCIAL ACCESS

Implement granular, server-enforced permissions for financial operations.

Reuse ChurchOS's existing roles and organizational entities wherever possible. Map existing roles to Finance permissions through an explicit, configurable authorization model rather than creating conflicting identities.

Support the following financial responsibilities.

### A. Senior Pastor / Pastor-in-Charge

Allow authorized pastors to:

- View financial summaries and performance dashboards.
- View income and expenditure by reporting period.
- Compare budget against actual performance.
- Review cash and bank positions, reconciliation status, and outstanding obligations.
- View aggregate giving trends.
- Review designated and restricted fund balances.
- Review project financial performance.
- Approve or reject assigned budgets and expenditure requests.
- Request clarification or supporting documents.
- Review required remittances and their status.
- View approved financial statements and audit exceptions.
- Export permitted reports.

Do not automatically grant unrestricted access to individual members' giving records, payroll, confidential welfare payments, or every accounting operation.

### B. Church Accountant

Allow authorized accountants to:

- Maintain the chart of accounts.
- Record and review financial transactions.
- Validate income and expense classifications.
- Review offering count sheets and collection handovers.
- Prepare payment vouchers and journal entries.
- Maintain cashbooks and bank records.
- Perform bank reconciliation.
- Manage supplier bills, reimbursements, advances, and outstanding obligations.
- Maintain budgets and prepare financial reports.
- Prepare period-end and year-end accounting procedures.
- Review ledger entries, supporting evidence, and transaction exceptions.
- Manage accounting corrections using authorized reversal and adjustment workflows.

Do not automatically allow an accountant to approve their own payment, execute their own payment, and reconcile it without the required independent controls.

### C. Treasurer / Finance Officer

Allow authorized finance officers to:

- Receive verified collections.
- Record deposits and cash movements.
- Prepare payment documentation.
- Process approved transactions according to assigned responsibilities.
- Track cash advances and settlements.
- Manage receipts and payment references.
- Review authorized financial reports.

Separate transaction preparation, payment authorization, execution, and reconciliation according to the church's configured control policy.

### D. Head Usher / Offering Counter

Allow authorized ushers to:

- View assigned services and collection sessions.
- Create collection count sheets.
- Record cash denominations and totals.
- Record offering categories and envelope totals.
- Participate in independent counting and verification.
- Submit count sheets.
- Record discrepancies and explanations.
- Confirm collection handovers when authorized.
- View assigned collection history and handover status.
- Print or download permitted collection summaries.

Ushers must not access the general ledger, unrelated financial records, individual members' complete giving histories, expenditure approval functions, or payment execution.

### E. Departmental Leaders

Allow departmental leaders to:

- View their department's approved budget.
- Submit expenditure requests.
- Upload invoices, receipts, quotations, and supporting documents.
- View their department's approved expenses, commitments, and remaining budget.
- Track request and payment statuses.
- View departmental reports.

They must not access unrelated departments' confidential financial transactions or approve their own requests unless explicitly permitted by a properly configured independent approval policy.

### F. Finance Committee

Allow authorized committee members to:

- Review proposed budgets and budget revisions.
- Review significant expenditure requests.
- Review financial statements and budget variances.
- Review restricted-fund utilisation.
- Review project spending.
- Record decisions and approval evidence.
- Review audit findings and remedial actions.

Committee membership must not automatically confer unrestricted accounting-editing rights.

### G. Internal / External Auditor

Provide controlled, read-only access to authorized records, including:

- General ledger entries.
- Income and expenditure evidence.
- Collection sheets and handover records.
- Payment vouchers and approval history.
- Bank reconciliation records.
- Reversals, adjustments, and period-lock history.
- Relevant audit logs and exception reports.

Auditors must not be able to modify financial transactions they are auditing.

### H. Church Members

Allow authenticated members to:

- View their own verified giving history.
- View tithe, offering, donation, and special-fund contributions attributed to them.
- Download or request giving statements.
- Access receipts.
- View pledge commitments and fulfilment.
- Report missing or incorrectly attributed payments.
- Give through supported payment channels.
- View published church financial summaries when authorized.

Members must never be able to retrieve another member's giving history or confidential financial records.

### I. Hierarchical Church Finance Users

Where ChurchOS already supports a church hierarchy, provide configurable reporting access for authorized Area, Zone, Province, Regional, or Headquarters finance officers.

Allow them to:

- View authorized subordinate churches.
- Review submitted financial reports.
- Monitor remittance obligations and payments.
- View consolidated reports within their assigned scope.
- Review outstanding submissions and discrepancies.

Never assume all churches follow the same reporting hierarchy or remittance rules. Reuse the existing hierarchy and require explicit permissions for each organizational scope.

Implement the following workflow:

1. Open a collection session.
2. Assign counters.
3. Record cash denomination counts and envelopes.
4. Record separate category totals.
5. Capture independent count confirmation by authorized counters.
6. Identify and resolve count discrepancies.
7. Submit the count sheet.
8. Record handover to the authorized finance officer.
9. Confirm the amount physically received.
10. Record the deposit or approved cash custody.
11. Match the deposit to bank evidence.
12. Complete finance verification.
13. Post the corresponding accounting entries.

Corrections must preserve the original values and require a reason and authorized approval.

## 19. BACKEND, DATABASE AND API REQUIREMENTS

All financial permissions must be enforced on the server.

Hiding buttons or menu items in the frontend is not sufficient.

Reuse the existing database and backend architecture. Add migrations or compatible schema extensions only where necessary.

Before migrating existing records:

1. Inspect the current schema.
2. Identify existing records and relationships.
3. Back up the relevant data using the available environment's established procedure.
4. Design backward-compatible migrations.
5. Preserve existing IDs and references wherever possible.
6. Validate record counts and financial totals before and after migration.
7. Test the rollback or recovery strategy.
8. Avoid destructive migrations and unapproved data deletion.

Implement appropriate database constraints, unique transaction references, foreign keys, validation, and transaction boundaries.

Prevent duplicate submissions and duplicate financial postings.

Use idempotency protection for payment callbacks and retryable financial operations.

Use database transactions when posting a financial transaction and its corresponding debit and credit entries.

Do not allow a partially posted financial transaction.

Validate all amounts, dates, categories, fund designations, and account references on the server.

Prevent cross-tenant access, insecure direct object references, unauthorized record updates, and privilege escalation.

Never trust tenant IDs, branch IDs, member IDs, or user permissions supplied by the client without server-side authorization.

Use the authenticated user's authorized context to determine accessible records.

Protect payment credentials, secrets, and sensitive bank information.

Do not expose secrets in frontend code or logs.

## 20. DATA INTEGRITY AND ACCOUNTING RULES

Enforce the following rules throughout Finance:

- Posted journals must balance.
- Every posted transaction must have a unique, traceable reference.
- Every transaction must be associated with the correct church tenant.
- Branch, fund, department, and project classifications must be validated against authorized records.
- Unverified collections must not be reported as fully verified income.
- Unconfirmed digital payments must not be treated as settled.
- Pledges must be distinguished from actual receipts.
- Approved expenses must be distinguished from paid expenses.
- Restricted funds must not be spent on unauthorized purposes.
- Posted financial records must not be silently deleted.
- Corrections must use authorized reversals or adjustments.
- Closed accounting periods must be protected against unauthorized changes.
- Reports must use consistent accounting rules and reporting periods.
- Reconciliations must preserve outstanding differences.
- Transfers between funds must not incorrectly create new income or expenditure.
- Inter-account transfers must not be counted as new external income or expenditure.
- Fund transfers must preserve the original transaction references and approval history.
- Dashboard totals must reconcile to the appropriate accounting records.

Use consistent transaction states and ensure state transitions are validated by the backend.

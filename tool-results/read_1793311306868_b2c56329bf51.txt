     1→# 04 — Technical Architecture and Data Model
     2→
     3→**What this is:** the build blueprint for a multi-tenant church management platform (ChMS): stack, tenancy, access control, schema, background processing, integrations, operations, and the decisions that are expensive to undo.
     4→
     5→**Who reads it:** the founding engineer(s), and anyone staffing, quoting or reviewing the build.
     6→
     7→**Scope and premises**
     8→
     9→- Team of 2–4 engineers, comfortable in TypeScript, no dedicated SRE.
    10→- Tenants: churches of 150–3,000 weekly attenders, single- and multi-campus, US-first (USD, US SMS, QuickBooks).
    11→- Surfaces: staff admin web app, member/donor web experience (mobile-first), check-in kiosk mode, public giving pages, REST API.
    12→- Out of scope for v1: native mobile apps, group chat, sermon media, payroll, child-care invoicing.
    13→- All money figures are USD list prices at the access date, excluding payroll, support tooling and pass-through payment/SMS fees.
    14→
    15→**Version:** v1.0 — 2026-10-29. Owner: engineering lead. Review trigger: first 100 paying churches, any tenancy change, or any change to the money model.
    16→

    18→
    19→## Summary
    20→
    21→Build a TypeScript modular monolith: one Next.js app (admin, member portal, public giving) plus a separate Node worker, PostgreSQL, and a Postgres-backed job queue. One codebase, one language, one deploy; split services only at a measured bottleneck. Tenancy is shared schema with `tenant_id` on every table, composite foreign keys, and row-level security as a backstop rather than the primary control. Members sign in passwordless; staff use SSO or password plus mandatory MFA, with TOTP/passkey required for finance. The model centres on people, not households, as the subject of attendance and giving; donations are an append-only ledger with fund splits; attendance is one row per person per event. Stripe Connect Standard accounts with direct charges keep each church as merchant of record. Infrastructure runs about $300/month at 100 churches, $2,300 at 1,000 and $14,500 at 10,000, before payment and SMS pass-through. Eight decisions are expensive to reverse; settle them before the first migration.

    38→## 1. Recommended stack
    39→
    40→### 1.1 The recommendation
    41→
    42→**TypeScript end to end, deployed as a modular monolith with two entrypoints.** Not microservices, not a separate admin SPA.
    43→
    44→| Layer | Choice | Reason |
    45→|---|---|---|
    46→| Runtime | Node 22 LTS or newer | Long support, native fetch, good profiler story |
    47→| Web | Next.js (current stable, App Router) + React | Server rendering for public giving pages, server actions for admin mutations, one component library for admin and member UI |
    48→| Worker | Separate Node process, same packages | Statement runs and imports must not share the request lifecycle or memory limit |
    49→| Language | TypeScript, `strict`, zod at every boundary | One schema validates forms, server actions and the public API |
    50→| Database | PostgreSQL 17+ (managed) | RLS, JSONB, full-text search, partitioning, mature backup tooling |
    51→| Data access | Drizzle ORM, raw SQL for reports | Typed schema, SQL escape hatch, explicit control of the session variable that drives RLS |
    52→| Jobs | graphile-worker (Postgres-backed) | Enqueue in the same transaction as the business write; no dual-write window |
    53→| Cache / rate limits | Redis, optional below 1,000 tenants | Only where Postgres is a poor fit: token buckets, hot caches |
    54→| UI | Tailwind + shadcn/ui | Own the components; no design-system migration later |
    55→| Auth | better-auth or Auth.js, wrapped by an in-house policy layer | Library handles tokens and OAuth; we own permissions |
    56→| Files | S3-compatible object storage (Cloudflare R2) | Cheap, no egress fees, presigned uploads |
    57→| Hosting | Containers on Fly.io or Render, managed Postgres | No Kubernetes at this team size |
    58→| Observability | OpenTelemetry + Sentry + hosted logs/metrics | Vendor-neutral instrumentation |
    59→
    60→```mermaid
    61→flowchart LR
    62→  B[Browser / PWA] --> CF[Cloudflare CDN + WAF]
    63→  CF --> WEB[Next.js app<br/>admin · member · public giving]
    64→  WEB --> PG[(PostgreSQL primary)]
    65→  WEB --> Q[[Job queue in Postgres]]
    66→  Q --> WK[Worker process]
    67→  WK --> PG
    68→  WK --> STR[Stripe Connect]
    69→  WK --> EM[Postmark / SES]
    70→  WK --> SMS[Twilio]
    71→  WEB --> OBJ[(Object storage)]
    72→  PG --> RR[(Read replica<br/>1,000+ tenants)]
    73→  WK --> OBJ
    74→```
    75→
    76→### 1.2 Why this shape
    77→
    78→- **One deployable until it hurts.** A 2–4 person team pays a high tax for network boundaries: contracts, versioning, local dev, tracing across services. A modular monolith with enforced package boundaries (ESLint `no-restricted-imports`) gives most of the isolation benefit at none of the operational cost.
    79→- **Two entrypoints, not two apps.** `web` and `worker` share `packages/core`, so a business rule (for example "a refund creates a reversal, never an edit") exists once.
    80→- **The extraction seams are known in advance.** Integrations live in `packages/integrations` behind interfaces; anything that talks to Stripe, Postmark, Twilio or QuickBooks can become a service later without touching domain code.
    81→- **Server rendering matters commercially.** Public giving pages and event pages need to load fast on a phone on church wifi and be indexable. A client-rendered admin SPA would add a second auth/session implementation for no user-visible gain.
    82→
    83→### 1.3 The serious alternative: Laravel monolith
    84→
    85→Laravel (current release) with Filament, Postgres, Redis queues and Horizon is the honest competitor, not Rails.
    86→
    87→| Criterion (weight) | TypeScript monolith | Laravel + Filament | Rails |
    88→|---|---|---|---|
    89→| Time to first paying church (25%) | 10–12 weeks | 8–10 weeks | 9–11 weeks |
    90→| Hiring pool at sub-$90k remote (20%) | Very large | Very large | Small, and priced higher |
    91→| One language from DB to UI (15%) | Yes | No (Blade/Livewire plus JS) | No (Hotwire plus JS) |
    92→| Type safety across DB → API → UI (15%) | End to end (Drizzle + zod) | Partial | Partial |
    93→| Built-in auth, MFA, queues, scheduler (10%) | Assemble from libraries | Included | Included |
    94→| Admin CRUD scaffolding (10%) | Assemble | Filament, very fast | ActiveAdmin/Avo |
    95→| Member-facing UI quality ceiling (5%) | High | Medium | Medium |
    96→| **Weighted fit for this product** | **Best** | Close second | Third |
    97→
    98→**Choose Laravel instead if** the founder is a PHP developer, or the first customer must be live in under ten weeks with one engineer. Everything else in this document still applies: the tenancy contract, permission model, schema and integration choices are framework-neutral.
    99→
   100→**Do not choose Rails** at this team size in 2026. The framework is excellent; the hiring pool at a church-software budget is not, and Hotwire makes the member-facing experience harder to differentiate than React does.
   101→
   102→### 1.4 What the recommended stack costs you
   103→
   104→| Gap | Cost | Mitigation |
   105→|---|---|---|
   106→| No admin scaffolding | 2–3 weeks | Build one `ResourceTable` + `ResourceForm` driven by column metadata; every CRUD screen after the third is configuration |

   144→## 2. Multi-tenancy
   145→
   146→### 2.1 The three options
   147→
   148→| Criterion | Shared schema + `tenant_id` + RLS | Schema per tenant | Database per tenant |
   149→|---|---|---|---|
   150→| Isolation strength | Logical; strong if RLS is forced | Logical; weaker tooling | Physical |
   151→| Migration at 1,000 tenants | One migration | 1,000 migrations per release, or a loop that will partially fail | 1,000 migrations, orchestrated |
   152→| Connection pooling | One pool | `search_path` per checkout, pooler-hostile | One pool per tenant, or a proxy |
   153→| Cross-tenant operations (billing, support, analytics) | Trivial | Painful | Very painful |
   154→| Per-tenant restore | Hard, needs export tooling | Easy | Easy |
   155→| Noisy neighbour | Possible | Possible | None |
   156→| Cost at 100 / 1,000 / 10,000 | $ / $ / $$$ | $$ / $$$ / prohibitive | $$$ / $$$$ / prohibitive |
   157→| Onboarding a new church | Insert rows | DDL + seed | Provision instance |
   158→| Realistic ceiling | 10,000+ tenants with partitioning and cells | Hundreds | Dozens |
   159→
   160→### 2.2 Recommendation
   161→
   162→**Shared schema, one primary database, `tenant_id` on every tenant-owned table, RLS forced on every one of them, composite foreign keys on money and membership edges.**
   163→
   164→Sizing check, assuming 700 people records and 300 weekly attendance rows per church:
   165→
   166→| Table | 100 churches | 1,000 churches | 10,000 churches |
   167→|---|---|---|---|
   168→| `people` (total rows) | 70k | 700k | 7M |
   169→| `attendance_records` (rows/year) | 1.6M | 15.6M | 156M |
   170→| `donations` (rows/year) | 300k | 3M | 30M |
   171→| `message_recipients` (rows/year) | 2.4M | 24M | 240M |
   172→| Database size after 3 years | ~15 GB | ~150 GB | ~1.5 TB |
   173→
   174→Up to 1,000 churches this is an unremarkable single Postgres instance. At 10,000 it is a partitioning and operations problem, not a schema problem: `message_recipients`, `attendance_records` and `audit_log` must be partitioned, and the estate should be split into cells of roughly 3,000–5,000 tenants (§2.5). Schema-per-tenant buys nothing here and costs a migration pipeline plus a pooler workaround. Database-per-tenant is reserved for contracted isolation.
   175→
   176→### 2.3 The implementation contract
   177→
   178→Non-negotiable rules, because each one has a known failure mode:
   179→
   180→1. **Every tenant-owned table has `tenant_id uuid not null`**, including join tables, and a composite index whose first column is `tenant_id`.
   181→2. **The application role is not the table owner and has no `BYPASSRLS`.** Migrations run as `app_migrator` (owner); the app connects as `app_rw`. PostgreSQL documents that owners bypass RLS unless `FORCE` is used, and that superusers and `BYPASSRLS` roles always bypass it ([PostgreSQL documentation, Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), accessed 2026-10-29).
   182→3. **`ENABLE` and `FORCE ROW LEVEL SECURITY` on every tenant table.** With RLS enabled and no policy, access is default-deny, which is the correct failure mode.
   183→4. **Tenant context is set per transaction, never per session.** `SET LOCAL` survives PgBouncer transaction pooling; a session-level `SET` leaks the previous tenant into the next request on a reused connection.
   184→5. **Repositories do not accept a tenant id argument.** They read it from an async context established by `withTenant()`, so a controller cannot pass the wrong one.
   185→6. **No raw SQL outside `packages/db` and report modules.** A lint rule bans `db.execute` elsewhere.
   186→
   187→```sql
   188→-- Migration 0001: the tenancy primitive
   189→create schema if not exists app;
   190→
   191→create or replace function app.current_tenant() returns uuid
   192→language sql stable as $$
   193→  select nullif(current_setting('app.tenant_id', true), '')::uuid
   194→$$;
   195→
   196→alter table people enable row level security;
   197→alter table people force row level security;
   198→
   199→create policy tenant_isolation on people
   200→  using (tenant_id = app.current_tenant())
   201→  with check (tenant_id = app.current_tenant());
   202→```
   203→
   204→```ts
   205→// packages/db/src/with-tenant.ts
   206→export async function withTenant<T>(
   207→  ctx: { tenantId: string; membershipId: string },
   208→  fn: (tx: Tx) => Promise<T>,
   209→): Promise<T> {
   210→  return db.transaction(async (tx) => {
   211→    await tx.execute(sql`select set_config('app.tenant_id', ${ctx.tenantId}, true)`);
   212→    await tx.execute(sql`select set_config('app.membership_id', ${ctx.membershipId}, true)`);
   213→    return fn(tx);
   214→  });
   215→}
   216→```
   217→
   218→**Composite foreign keys** are the second lock on the door. RLS filters rows a query can see; it does not stop a row in tenant A from pointing at a row in tenant B if the application supplies the id. Composite keys make that structurally impossible:
   219→
   220→```sql
   221→alter table donations
   222→  add constraint donations_person_fk
   223→  foreign key (tenant_id, person_id) references people (tenant_id, id);
   224→```
   225→
   226→Every parent table then needs `unique (tenant_id, id)`. That is one extra index per table and worth it for `donations`, `donation_splits`, `attendance_records`, `group_members`, `memberships` and `role_assignments`.
   227→
   228→**RLS does not cover everything.** Referential integrity checks bypass row security by design (same PostgreSQL page), so a foreign-key violation can reveal that an id exists in another tenant. Map every `23503` to a generic `422 invalid reference`, never echo the constraint or the id. `TRUNCATE` and `REFERENCES` are also outside RLS.
   229→
   230→### 2.4 Where this breaks, and what to do
   231→
   232→| Failure mode | Symptom | Mitigation |
   233→|---|---|---|
   234→| A new query forgets `tenant_id` | Cross-tenant rows in a list, or an empty list | RLS backstop returns only the current tenant; leak suite fails CI |
   235→| Session-level `SET` on a pooled connection | One church sees another's data intermittently | Only `withTenant()` may open a transaction; lint rule; integration test that reuses a connection across two tenants |
   236→| Long report inside a tenant transaction | Pool exhaustion at 11am Sunday | Reports run on the replica, `statement_timeout = 30s`, no interactive transaction |
   237→| Missing index with `tenant_id` first | Sequential scans as soon as one big tenant arrives | `pg_stat_user_tables` review each release; index every FK |
   238→| Tenant bulk import | CPU spike, check-in latency | Import concurrency capped at 2, chunk size 1,000, separate worker pool |
   239→| RLS policy drift | A new table ships without a policy | Migration test asserts every table with `tenant_id` has `relrowsecurity` and `relforcerowsecurity` |
   240→
   241→### 2.5 Isolation path for a large multi-campus customer
   242→
   243→Some customers will ask for a dedicated database: a 3,000-attender multi-campus church with a security questionnaire, or a denomination that wants contractual separation. The answer is a **cell architecture** with tenant routing, designed now and built on first demand.
   244→
   245→| Phase | Trigger | Work | Effort |
   246→|---|---|---|---|
   247→| 0. Design for exit | Day one | No cross-tenant joins; UUIDv7 ids generated in app; `tenant_id` everywhere; composite FKs; all access through repositories; object keys prefixed `t/{tenant_id}/`; a `tenant_export` job exists from month one | Continuous, ~0 |
   248→| 1. Export tool | First enterprise conversation | Stream NDJSON per table in FK order into object storage, with row counts and checksums | 3–5 days |
   249→| 2. Dedicated cell | Signed contract | Provision a database, run the same migrations, import, verify counts and checksums, shadow-read for a week | 2–3 days |
   250→| 3. Cutover | Maintenance window | Freeze writes (app-level tenant lock), final delta import, flip `tenant_routing.cell_id`, 60-minute soak, rollback = flip back | 2-hour window |
   251→| 4. Steady state | After | Per-cell backups, staged migrations per cell, per-cell capacity dashboard, isolation priced into the contract | Ongoing, ~2 hours/month |
   252→
   253→Design rules that make phase 3 boring:
   254→
   255→- **Ids are globally unique and time-sortable** (UUIDv7 generated in the application, not `gen_random_uuid()`), so no sequence re-basing and no id collision across cells.
   256→- **A control-plane table `tenant_routing(tenant_id, cell_id, dsn_secret_ref)`** lives in a small separate database that never holds tenant content. The app resolves the connection per request; today every row points at `primary`.
   257→- **No cross-tenant foreign keys, ever.** This is also what makes the shared schema safe.
   258→- **Do not use logical replication for the move.** It does not carry DDL, and sequence state needs separate handling; a logical export plus import is simpler and verifiable for a 50–500 MB tenant. Re-verify this on the Postgres major version you deploy.
   259→- **Charge for isolation.** It is a permanent operational cost (separate backups, separate migration runs, separate monitoring). Price it as a platform fee, not a one-off setup fee.
   260→
   261→An intermediate "schema-per-tenant, same database" tier is not worth building. It has the migration cost of schema-per-tenant without the isolation benefit of a separate database.

   265→## 3. Auth and permissions
   266→
   267→### 3.1 Identity model
   268→
   269→Three nouns, deliberately separate:
   270→
   271→- **`users`** — a login identity, global, unique by email. One human, one user, even if they serve two churches.
   272→- **`memberships`** — binds a user to a tenant and (usually) a person record, with a status and a default campus. This is what a session activates.
   273→- **`people`** — the pastoral record. Most people never have a user: children, deceased members, imported records, first-time guests.
   274→
   275→Invariants:
   276→
   277→1. A person may exist without a user; a user may exist without a person (a contractor).
   278→2. At most one membership per `(user, tenant)` and one per `(tenant, person)`.
   279→3. Removing a membership never deletes the person or their giving history.
   280→4. A person can be staff at one church and a donor at another with a single login.
   281→5. Staff accounts are invite-only. Only member-facing signup may create a user implicitly.
   282→
   283→### 3.2 Authentication by audience
   284→
   285→| Audience | Primary | Fallback | Notes |
   286→|---|---|---|---|
   287→| Members, donors | Email magic link | SMS one-time code | No password by default; password optional later if support load demands it |
   288→| Volunteers, group leaders | Email magic link | Password | 30-day session |
   289→| Staff | Google or Microsoft SSO when the email domain is claimed | Email + password, Argon2id | Domain claim auto-provisions and auto-deprovisions |
   290→| Finance | SSO or password + TOTP | Passkey | MFA mandatory, SMS factors not allowed |
   291→| Org admins | SSO + passkey preferred | TOTP | Step-up re-auth for role and billing changes |
   292→| Check-in kiosks | Device pairing code | — | 90-day device token, campus-bound, revocable per device |
   293→| API clients | API key, hashed at rest | OAuth2 apps later | Scoped, optionally campus-bound |
   294→
   295→### 3.3 Magic link flow
   296→
   297→1. `POST /auth/magic-link { email, tenantSlug? }` always returns `202`, whether or not the account exists.
   298→2. Rate limit: 5 per hour per email, 20 per hour per IP, constant-time lookup.
   299→3. Token: 32 random bytes, stored as SHA-256, 15-minute TTL, single use, bound to the email and optional tenant.
   300→4. Email sent through Postmark with the tenant's branding and a plain-text fallback.
   301→5. `GET /auth/verify?token=[redacted] consumes the token atomically (`update … where used_at is null returning`), creates a session, rotates the session id.
   302→6. If the user has more than one membership, show a tenant chooser and remember the last choice.
   303→
   304→Do not put the token in a URL that a mail scanner will prefetch and burn. Either require a POST confirm page, or accept a scanner-tolerant design where the token is single-use only after the confirm click.
   305→
   306→### 3.4 MFA policy
   307→
   308→| Scope | Required | Allowed factors | Enforcement | Step-up |
   309→|---|---|---|---|---|
   310→| Platform operators (us) | Yes | Hardware passkey, TOTP | Before any production access | Every production write |
   311→| Org admin | Yes | Passkey, TOTP | 7-day grace, then login blocked | 15 minutes for roles, billing, API keys |
   312→| Finance roles | Yes | TOTP, passkey; **no SMS** | Blocked at grant time | 15 minutes for refunds, statement sends, bank changes |
   313→| Other staff | Yes | TOTP, passkey | 14-day grace | Not required |
   314→| Group leaders | No | TOTP | Optional | Not required |
   315→| Members, donors | No | Passkey | Optional | Not required; Stripe handles 3-D Secure |
   316→
   317→SMS one-time codes are acceptable as a member convenience factor, never as a second factor for finance. SIM-swap and number-recycling attacks target exactly the demographic that church finance volunteers belong to.
   318→
   319→### 3.5 Sessions
   320→
   321→| Property | Staff | Member |
   322→|---|---|---|
   323→| Cookie | `__Host-chms_sid`; HttpOnly, Secure, SameSite=Lax, Path=/, no Domain | Same |
   324→| Token | 256-bit random; SHA-256 stored in `sessions.id` | Same |
   325→| Idle timeout | 12 hours | 30 days |
   326→| Absolute lifetime | 30 days | 180 days |
   327→| Rotation | On login, MFA, role change, password change | On login |
   328→| Concurrent sessions | 5, oldest revoked | 10 |
   329→| Revocation | Self-service device list; admin force-logout | Same |
   330→| Sensitive actions | Require `mfa_at` within 15 minutes | n/a |
   331→
   332→`amr` records how the session authenticated (`pwd`, `sso`, `magic_link`, `totp`, `passkey`); `mfa_at` records the last strong authentication. Authorisation for refunds, statement sends and role changes checks both.
   333→
   334→### 3.6 RBAC schema
   335→
   336→```sql
   337→create table roles (
   338→  id uuid primary key,
   339→  tenant_id uuid not null references organizations(id),
   340→  key text not null,                    -- 'finance_admin', 'campus_pastor', 'group_leader'
   341→  name text not null,
   342→  is_system boolean not null default false,
   343→  created_at timestamptz not null default now(),
   344→  unique (tenant_id, key)
   345→);
   346→
   347→create table role_permissions (
   348→  role_id uuid not null references roles(id) on delete cascade,
   349→  permission text not null,             -- 'donation:refund'; validated against the code catalogue
   350→  primary key (role_id, permission)
   351→);
   352→
   353→create table role_assignments (
   354→  id uuid primary key,
   355→  tenant_id uuid not null references organizations(id),
   356→  membership_id uuid not null references memberships(id) on delete cascade,
   357→  role_id uuid not null references roles(id),
   358→  scope_type text not null check (scope_type in ('org','campus','group')),
   359→  scope_id uuid,
   360→  granted_by uuid references users(id),
   361→  granted_at timestamptz not null default now(),
   362→  expires_at timestamptz,
   363→  check ((scope_type = 'org' and scope_id is null)
   364→      or (scope_type <> 'org' and scope_id is not null))
   365→);
   366→
   367→create unique index role_assignments_unique
   368→  on role_assignments (membership_id, role_id, scope_type,
   369→                       coalesce(scope_id, '00000000-0000-0000-0000-000000000000'::uuid));
   370→```
   371→
   372→`scope_id` is polymorphic (a campus id or a group id), so it cannot carry a foreign key. Enforce it with a `before insert or update` trigger that checks existence in the table implied by `scope_type`, and delete assignments in the same transaction when a campus or group is deleted.
   373→
   374→Permission codes are constants in `packages/auth/permissions.ts`, not rows. A misspelled permission in a role is caught at startup and by a CI test that asserts every code in `role_permissions` exists in the catalogue. This removes a migration from the permission lifecycle and keeps code review honest.
   375→
   376→### 3.7 Scope resolution
   377→
   378→| `scope_type` | `scope_id` | Grants | Example role |
   379→|---|---|---|---|
   380→| `org` | `null` | Every campus in the tenant | Lead pastor, finance admin |
   381→| `campus` | `campuses.id` | Rows belonging to that campus, plus org-wide reference data (funds, role templates) | Campus pastor |
   382→| `group` | `groups.id` | That group's roster, meetings, attendance and messages | Group leader |
   383→
   384→Resolution is `has(permission) AND scopeCovers(target)`. Because both halves are needed, the call site always passes the target: `authorize(session, 'donation:refund', { campusId })`. A permission check without a target is only valid for org-scoped resources such as funds or role templates.
   385→
   386→Campus-scoped roles do not inherit org-level visibility of people. A campus pastor assigned to North Campus sees North Campus people, not the whole church. This is the single most common support complaint in incumbent ChMS products, in both directions; make it a per-role flag (`scope_includes_org_read`) rather than a hard-coded rule.

   434→### 3.10 Enforcement layers
   435→
   436→| Layer | Stops | Implemented in |
   437→|---|---|---|
   438→| Route guard | Unauthenticated requests, missing permission | Middleware and every server action |
   439→| Scope filter | Wrong-campus access | Repository query builder, using the session's scope set, never client input |
   440→| Row-level security | Missing tenant filter | Postgres policy |
   441→| Field projection | Seeing amounts or notes you may not see | Serializer per audience |
   442→| Step-up auth | Refund, statement send, role change, bank change | `mfa_at` check in the handler |
   443→| Audit | Repudiation | `audit_log` write in the same transaction |

   445→### 3.11 Edge cases worth designing now
   446→
   447→- **Staff who are also donors.** One person row, one membership; the admin app never shows their own giving, and the member portal does. Do not create a second person record for the staff member.
   448→- **Group leaders** see name, photo, phone and allergy notes for their own group only. Not addresses, not giving, not household relationships.
   449→- **Campus pastors** get aggregate giving by default; individual detail requires `report:giving_detail`.
   450→- **Separation of duties in finance.** A batch created by one user above a configurable threshold must be posted by another with `batch:post`. Implement with `batches.created_by` plus a pending state; do not add an approvals table in v1.
   451→- **Children turning 18.** A nightly job flags people whose 18th birthday passed, expires guardian relationships, and opens a review task for the admin.
   452→- **Merging duplicate people.** Repoint every foreign key in one transaction, set `merged_into_id`, write an `audit_log` entry containing both snapshots, and keep the loser row soft-deleted for 30 days. Merge is the one operation that is genuinely hard to reverse; require `people:merge` and show a preview of affected donations, attendance and group memberships.

   456→## 4. Core data model
   457→
   458→### 4.1 Conventions
   459→
   460→| Rule | Decision |
   461→|---|---|
   462→| Primary keys | UUIDv7, generated in the application; time-sortable, shard-safe, index-friendly |
   463→| Tenant key | `tenant_id` on every tenant-owned table, first column of every composite index |
   464→| Referential integrity | Composite FKs `(tenant_id, x_id)` on money, membership and attendance edges; plain FKs elsewhere |
   465→| Money | `amount_cents bigint` plus `currency char(3)`. No floats, no negative donations; corrections are reversals |
   466→| Time | `timestamptz` in UTC; `date` for service and received dates; `organizations.timezone` (IANA) decides day boundaries |
   467→| Soft delete | `deleted_at` on `people`, `groups`, `messages`, `files`. Money and attendance are never deleted |
   468→| Naming | `snake_case`, plural tables, singular columns, `_id` suffix |
   469→| Enums | Postgres enum for stable sets (donation status), `text` + `check` for sets that will grow (event kind) |
   470→| Audit | Every write to money, permissions and people goes through the audit service in the same transaction |
   471→| PII | Email lower-cased, phone in E.164; no PII in logs or error messages |

   811→### 4.4 Constraints you must actually create
   812→
   813→1. `unique (tenant_id, id)` on every table used as a composite FK target.
   814→2. Composite FKs on `donations`, `donation_splits`, `attendance_records`, `group_members`, `memberships`, `role_assignments`.
   815→3. `unique (tenant_id, event_id, person_id)` on `attendance_records`.
   816→4. `unique (tenant_id, source, external_id)` on `donations` where `external_id is not null`.
   817→5. `unique (tenant_id, idempotency_key)` on `donations` where `idempotency_key is not null`.
   818→6. Deferred constraint trigger: `sum(donation_splits.amount_cents) = donations.amount_cents` at commit.
   819→7. `check (amount_cents > 0)` on `donations` and `donation_splits`; `check (currency = upper(currency))`.
   820→8. `unique (group_id, person_id) where left_at is null` on `group_members`.
   821→9. `unique (provider, provider_event_id) where direction = 'inbound'` on `webhook_events`.
   822→10. **No unique index on `people.email`.** Families share an address, parents use their own for a child's record, and imported data is messy. Uniqueness is a merge recommendation, not a constraint.
   823→
   824→### 4.5 Index rules
   825→
   826→| Rule | Reason |
   827→|---|---|
   828→| Every composite index leads with `tenant_id` | Tenant pruning; RLS adds the same predicate |
   829→| `(tenant_id, created_at desc)` for list screens | Stable keyset pagination |
   830→| Partial indexes `where deleted_at is null` | Smaller, hotter indexes |
   831→| GIN on `people.search` (`tsvector`) and on `custom jsonb_path_ops` | Name search and custom-field filters |
   832→| BRIN on `created_at` for append-only tables above 100M rows | Cheap range pruning for audit and message logs |
   833→| Maximum six indexes per table | `donations` is write-heavy; every index is write amplification |
   834→| Drop unused indexes quarterly | `pg_stat_user_indexes.idx_scan = 0` |
   835→
   836→### 4.6 Custom fields: definitions plus JSONB, not EAV
   837→
   838→`custom_field_definitions` holds the per-tenant schema. Values live in a `custom jsonb` column on `people`, `groups`, `events` and `donations`, validated on write against a per-tenant zod schema compiled from the definitions and cached for five minutes.
   839→
   840→| Option | Read cost for a 5,000-person list | Type safety | Schema change | Verdict |
   841→|---|---|---|---|---|
   842→| EAV (`custom_field_values` rows) | 8 fields × 5,000 people = 40,000 joins per screen | None without casting | Insert rows | Rejected |
   843→| `ALTER TABLE` per tenant | Fast | Full | DDL locks, thousands of columns | Rejected |
   844→| JSONB on the entity | One row, one GIN index when needed | Validated by zod at the edge | Insert a definition row | **Chosen** |
   845→
   846→When a customer needs to filter or sort by a custom field across more than ~100k rows, add `custom_field_index(entity_type, entity_id, field_key, value_text, value_num, value_date)` maintained by trigger, and only for definitions marked `searchable`. Do not build it on day one.
   847→
   848→### 4.7 Three decisions that are expensive to reverse
   849→
   850→**1. The person is the atomic subject; the household is a grouping.**
   851→Every donation, attendance record and group membership points at a person. `households` exists for addresses, statements and "family" views, with `is_statement_unit` deciding whether the year-end statement is per person or per household. The alternative, keying gifts to a household, looks simpler for a married couple and collapses on the first divorce, the first adult child who gives separately, and the first anonymous cash gift. Reversing it means re-attributing every historical gift, reissuing statements, and explaining the change to donors. Estimated cost: 4–8 weeks plus a donor-visible correction.
   852→
   853→**2. Money is an append-only ledger with fund splits.**
   854→A posted donation is never edited. Corrections are a new row with `reversal_of_id`; refunds reduce net without changing the original amount; a bounced check is a reversal plus a fee line. Fund allocation lives only in `donation_splits`, so one gift can span general and building funds, and a deferred trigger guarantees the splits sum to the header. Fees are recorded (`fee_cents`, `net_cents`) but never netted into the gift, because the donor's statement must show what they gave, not what the church received.
   855→If you allow in-place edits, you lose the ability to answer "what did we tell this donor in January" and you cannot support an audit. Reversing this is a reporting rewrite plus a data reconstruction project.
   856→
   857→**3. Tenant key and id strategy: UUIDv7, `tenant_id` everywhere, composite FKs.**
   858→Adding `tenant_id` to a 400 GB table later requires a full rewrite with an exclusive lock, and every query, index and unique constraint changes with it. Choosing integer sequences now means a re-basing exercise at the first isolated cell. The composite FKs are what make cross-tenant leakage structurally impossible rather than merely unlikely. Cost to reverse at 1,000 tenants: 3–6 weeks with downtime risk.
   859→
   860→**Honourable mention: attendance grain.** One row per person per event, with `status` covering present, absent, excused and late. The tempting shortcut is to store only present rows and infer absence from the roster, but rosters change: people leave groups, guests attend once, a family moves campuses. Historical absence then silently rewrites itself. Write `absent` rows when a session closes and the history stays true. Cost to reverse: the historical absence data is simply gone.
   861→

   878→### 5.1 Jobs and schedulers
   879→
   880→**Queue: Postgres, not Redis.** graphile-worker stores jobs as rows, so a job can be enqueued inside the same transaction as the donation it belongs to. With Redis, the commit can succeed and the enqueue fail, and the gift is never receipted. Throughput needs are modest: tens of jobs per second at 10,000 churches, bursting into the hundreds on Sunday morning, against a Postgres queue that handles thousands.
   881→
   882→| Job | Trigger | Cadence / limit | Idempotency key | Notes |
   883→|---|---|---|---|---|
   884→| `absence_detect` | Check-in session closes, or roster submitted | Per event, within 5 minutes | `absence:{event_id}` | Writes `absent` rows for expected people, then fires absence workflows |
   885→| `event_materialise` | Weekly, plus on service edit | 8 weeks ahead | `evt:{service_id}:{date}` | Generates occurrences from `rrule`, DST-safe |
   886→| `attendance_rollup` | Nightly | 02:00 tenant local | `rollup:{tenant}:{date}` | Daily per-campus and per-service totals |
   887→| `giving_rollup` | Nightly | 02:30 tenant local | `giving_rollup:{tenant}:{date}` | Fund and campus totals |
   888→| `statement_generate` | January window, or on demand | 10 tenants/minute aggregate, workers scale | `statement:{tenant}:{year}` | Fan-out per person; PDF to object storage |
   889→| `recurring_gift_charge` | Scheduler scan | Every 15 minutes | `rg:{id}:{scheduled_for}` | Off-session PaymentIntent on the saved method |
   890→| `dunning` | `payment_intent.payment_failed` | T+1, T+3, T+7 | `dunning:{donation_id}:{attempt}` | Then `past_due`, notify donor and finance |
   891→| `stripe_reconcile` | Daily | 03:00 UTC | `recon:{date}` | Compares balance transactions with donations |
   892→| `webhook_deliver` | Event insert | Continuous, 6 attempts | `wh:{event_id}` | Backoff 1m, 5m, 30m, 2h, 6h, 24h, then dead-letter |
   893→| `import_chunk` | Import start | 1,000 rows per chunk, concurrency 2 | `import:{job_id}:{chunk}` | Streaming parse, per-row error capture |
   894→| `export_tenant` | Admin or contract request | On demand | `export:{tenant}:{request_id}` | NDJSON per table plus checksums |
   895→| `purge_soft_deleted` | Nightly | 03:30 | `purge:{date}` | 30-day retention, then hard delete |
   896→| `session_gc`, `idempotency_gc` | Nightly | 04:00 | `gc:{date}` | Bounded deletes in batches |
   897→
   898→Scheduler mechanics:
   899→
   900→- One leader elected with `pg_try_advisory_lock(hashtext('scheduler'))`; every worker can be a candidate, exactly one runs cron.
   901→- Cron expressions are code, not database rows, so a deploy and a schedule cannot drift.
   902→- Per-tenant schedules store local time plus timezone and are converted to UTC on each tick. Test the spring-forward gap explicitly: 02:30 does not exist on one day a year, and a naive scheduler either skips or double-runs that day.
   903→- Missed runs are caught up on startup with a `missed_run` flag, not silently skipped. A worker outage at 02:00 must not lose a day of rollups.
   904→- Every handler is idempotent and safe to run twice. That is the requirement, not a nice-to-have.
   905→
   906→### 5.2 Idempotency
   907→
   908→**Inbound webhooks (Stripe, Postmark, Twilio):**
   909→
   910→1. Verify the signature before parsing the body; reject with `400` and log the provider and timestamp only.
   911→2. `insert into webhook_events (provider, provider_event_id, …) on conflict (provider, provider_event_id) do nothing returning id`.
   912→3. If no row was returned, the event is a duplicate: return `200` immediately.
   913→4. Otherwise enqueue processing and return `200` in under two seconds. Never do the work inline; providers time out and retry, which multiplies the problem.
   914→5. The handler re-reads the provider object (do not trust the payload for money) and writes in one transaction.
   915→6. Failed events stay `failed` with `last_error`; a support screen can replay them, and replay uses the same dedupe path.
   916→
   917→**Outbound API:** `Idempotency-Key` header on every `POST` and `PATCH`. Store `(tenant_id, key, endpoint, request_hash, response_status, response_body, expires_at)` in `idempotency_keys` for 24 hours. Same key with a different body returns `409`; same key returns the stored response. This table is infrastructure, not part of the 40-table domain count, alongside the job queue and migration tables.
   918→
   919→**Jobs:** graphile-worker's unique `job_key` covers the common case; for multi-step work the handler also checks state (`workflow_runs.idempotency_key`, `donations.idempotency_key`) before acting.

   935→### 5.4 Search
   936→
   937→- Postgres full-text search on `people.search` (name, email, phone, preferred name) plus `pg_trgm` similarity for misspellings; rank exact email/phone first, then name prefix, then trigram.
   938→- Search is always tenant-scoped by RLS and campus-filtered by the repository. Never index giving notes or pastoral notes into the search vector.
   939→- A global GIN index on a shared table is fine because `tenant_id` is highly selective; the index stays usable up to a few million people rows.
   940→- Add Typesense or Elasticsearch only when cross-entity search with facets becomes a product requirement, not before 5,000 tenants.

   942→### 5.5 Reporting
   943→
   944→| Scale | Approach | Why |
   945→|---|---|---|
   946→| < 300 tenants | Live SQL with covering indexes, 60-second cache on dashboards | Simplest; queries are milliseconds at this size |
   947→| 300–3,000 | Nightly rollup tables (`attendance_daily`, `giving_monthly`) plus a read replica for ad-hoc reports | Predictable p95 without a warehouse |
   948→| 3,000–10,000 | Rollups, replica, per-tenant cached report payloads for the dashboard | Keeps the primary for writes |
   949→| > 10,000, or product analytics | Columnar warehouse (ClickHouse or BigQuery) fed by CDC | Analytics stops competing with check-in |
   950→
   951→Materialised views are a trap in a multi-tenant database. `REFRESH MATERIALIZED VIEW` refreshes every tenant's data at once, and `CONCURRENTLY` needs a unique index and still scans the whole view; per-tenant freshness is impossible without partitioning per tenant. Use rollup tables written by jobs, keyed `(tenant_id, date, campus_id)`, with a unique index that makes the job idempotent.
   952→
   953→Reports run as `app_read` on the replica with `statement_timeout = 30s`. Individual-level giving reports require `report:giving_detail`; aggregate reports go through a separate repository method that never selects `person_id`.

   955→### 5.6 Import and migration from incumbents
   956→
   957→Pipeline:
   958→
   959→1. **Upload** CSV or XLSX to object storage; record `import_jobs` with checksum.
   960→2. **Sniff** encoding, delimiter and header row; show the first 20 rows back to the user.
   961→3. **Map** columns to fields, with a saved mapping per source system (`planning_center`, `ccb`, `breeze`, `tithe_ly`, `generic`).
   962→4. **Validate** into a staging table: dates, phones to E.164, emails lower-cased, fund names resolved, unknown values flagged.
   963→5. **Dedupe preview**: candidate matches with confidence, side by side, human decision per row. Never auto-merge.
   964→6. **Commit** in 1,000-row chunks, each its own transaction, stamped with `import_batch_id`.
   965→7. **Report**: created, updated, skipped, failed with row numbers, downloadable as CSV.
   966→8. **Rollback** within 7 days: delete rows created by the batch, revert merges from the stored merge log, keep an audit entry either way.
   967→
   968→| Match rule | Confidence | Action |
   969→|---|---|---|
   970→| Exact email, same tenant, not soft-deleted | High | Pre-select merge |
   971→| Exact E.164 phone | High | Pre-select merge |
   972→| Name + birthdate | Medium | Suggest, require confirmation |
   973→| Name + household address | Medium | Suggest, require confirmation |
   974→| Name only | Low | Never merge; create and flag |
   975→
   976→| Incumbent | Export path | Known friction |
   977→|---|---|---|
   978→| Planning Center People | CSV export, or API with an app credential | Households and custom fields need remapping; child dedications are not people |
   979→| Church Community Builder | CSV export per list | Individual giving and household giving use different keys |
   980→| Breeze | CSV export | Phone formats vary by household member |
   981→| Tithe.ly | CSV giving export plus member export | Funds are named inconsistently across years |
   982→| Fellowship One / Rock | CSV or direct database export on contract | Custom schemas; expect a bespoke mapping per customer |
   983→
   984→Flag: verify each export format at build time; all five vendors change exports without notice. Budget one bespoke mapping per enterprise migration, charged as onboarding.

   990→### 6.1 Stripe Connect
   991→
   992→| Model | Money lands in | Merchant of record | Stripe fees | Connect fees to us | Our exposure |
   993→|---|---|---|---|---|---|
   994→| **Direct charges on Standard accounts** | The church's Stripe balance | The church | Church pays 2.9% + 30¢ | None | Low: we never hold funds |
   995→| Destination charges | Our platform balance, then transferred | Us | We pay | $2/active account/month + 0.25% + 25¢ per payout, if we set pricing | Medium: disputes, reserves, refunds |
   996→| Separate charges and transfers | Our platform balance until transfer | Us | We pay | Same, plus transfer operations | High: we hold other people's money |
   997→
   998→Stripe's own documentation states that with direct charges the connected account is responsible for Stripe fees, refunds and chargebacks ([Stripe Connect pricing](https://stripe.com/connect/pricing), accessed 2026-10-29).
   999→
  1000→**Recommendation: Standard connected accounts with direct charges.** The church owns its donor relationship, its receipts, its dispute history and its tax reporting. We charge a SaaS subscription, never a percentage of gifts. Taking a cut of donations invites charity-regulation scrutiny, complicates receipts, and is the single fastest way to lose trust with a finance committee.
  1001→
  1002→Flow:
  1003→
  1004→1. Admin clicks "Connect giving" → Stripe-hosted onboarding for a Standard account.
  1005→2. `account.updated` webhook stores `charges_enabled`, `payouts_enabled`, `requirements.currently_due`; giving stays disabled until `charges_enabled` is true.
  1006→3. Donor pays via Stripe Elements or Checkout on the church's connected account; we never see card data (PCI SAQ A).
  1007→4. `payment_intent.succeeded` creates the donation, splits and receipt; `payment_intent.payment_failed` creates a failed attempt for dunning.
  1008→5. ACH (`us_bank_account` via Financial Connections) stays `pending` for 3–5 business days until `charge.succeeded`; the UI must say so.
  1009→6. Daily reconciliation compares Stripe `balance_transactions` with `donations`; unmatched items go to an ops queue, never silently adjusted.

  1011→Recurring gifts: run our own scheduler with off-session PaymentIntents rather than Stripe Subscriptions.

  1014→|---|---|---|---|---|
  1015→| Own scheduler + saved payment method | Full (T+1, T+3, T+7, custom) | Exact | Exact | Medium |
  1016→| Stripe Subscriptions | Smart Retries, limited control | One price per subscription | Approximate | Low |

  1072→
  1073→| Resource | Endpoints | Scopes |
  1074→|---|---|---|
  1075→| People | `GET/POST/PATCH /v1/people`, `GET /v1/people/{id}` | `people:read`, `people:write` |
  1076→| Households | `GET/POST/PATCH /v1/households` | `people:read`, `people:write` |
  1077→| Groups | `GET /v1/groups`, `GET /v1/groups/{id}/members` | `groups:read` |
  1078→| Events | `GET /v1/events`, `GET /v1/events/{id}/attendance` | `events:read` |
  1079→| Attendance | `POST /v1/attendance` | `attendance:write` |
  1080→| Donations | `GET /v1/donations`, `GET /v1/funds` | `giving:read` |
  1081→| Pledges | `GET /v1/pledges` | `giving:read` |
  1082→| Messages | `POST /v1/messages` | `messages:write` |
  1083→| Webhooks | `GET/POST/DELETE /v1/webhook_endpoints` | `webhooks:manage` |
  1084→
  1085→Conventions:
  1086→
  1087→- REST + JSON, `/v1` in the path; additive changes only within a version; deprecation announced with a `Sunset` header and 12 months' notice.
  1088→- Cursor pagination (`?cursor=&limit=`), `updated_since` for delta sync, `fields=` for sparse responses.
  1089→- Rate limit 600 requests/minute per key, burst 60; `429` with `Retry-After`.
  1090→- Errors as `application/problem+json` (RFC 9457) with a stable `code`, never a stack trace.
  1091→- Keys are shown once, stored hashed, scoped, optionally campus-bound, and revocable.
  1092→- Webhooks: `X-Chms-Signature: t=…,v1=HMAC-SHA256(secret, t + "." + body)`, 5-minute tolerance, at-least-once delivery, 6 retries, dead-letter after 24 hours. Consumers must dedupe on `event.id`.
  1093→
  1094→Event catalogue (v1): `person.created`, `person.updated`, `person.merged`, `household.updated`, `group.membership_changed`, `attendance.checked_in`, `donation.succeeded`, `donation.refunded`, `pledge.created`, `message.delivered`, `message.bounced`.
  1095→
  1096→Every payload carries `id`, `type`, `api_version`, `tenant_id`, `occurred_at` and `data`. Churches with in-house tools mostly want three things: people in, attendance out, giving out. Ship those three well before anything else.

  1100→## 7. Operations
  1101→
  1102→### 7.1 Environments
  1103→
  1104→| Environment | Purpose | Data | Notes |
  1105→|---|---|---|---|
  1106→| Local | Development | Seeded: 2 tenants × 300 people | Docker Compose: Postgres, Mailpit, MinIO; Stripe CLI for webhooks |
  1107→| Preview | Per pull request | Ephemeral database branch, seeded | Auto-destroy after 7 days; URL posted on the PR |
  1108→| Staging | Release candidate and migration rehearsal | Synthetic tenant plus an anonymised copy on request | Stripe test mode, Twilio test credentials, separate Postmark server |
  1109→| Production | Customers | Real | Multi-AZ database, 2+ app instances, worker pool, replica at 1,000+ tenants |
  1110→
  1111→Separate credentials per environment for every provider. A test-mode Stripe key in production is a silent revenue bug; a live key in staging is worse.
  1112→
  1113→### 7.2 CI/CD
  1114→
  1115→| Stage | Tool | Gate |
  1116→|---|---|---|
  1117→| Lint and format | Biome or ESLint + Prettier | Required |
  1118→| Typecheck | `tsc --noEmit` | Required |
  1119→| Unit | Vitest | 80% on `packages/core` |
  1120→| Integration | Testcontainers Postgres | Migrations apply cleanly from zero |
  1121→| **Tenant leak suite** | Vitest + two seeded tenants | Every endpoint and repository returns zero cross-tenant rows |
  1122→| RLS coverage | SQL assertion | Every table with `tenant_id` has `relrowsecurity` and `relforcerowsecurity` |
  1123→| E2E | Playwright | 12 flows: sign-in, check-in, gift, refund, import, statement, role change |
  1124→| Migration review | `drizzle-kit generate` diff | Destructive changes blocked unless labelled `expand-contract` |
  1125→| Deploy | Container build, rolling release | Health check plus 5-minute error-rate watch |
  1126→
  1127→Migration discipline: **expand → backfill → contract**, one release apart. Add nullable columns, backfill in a job, switch reads, drop the old column in a later release. Never combine a destructive migration with a code deploy that still reads the old shape. For large tables use `CREATE INDEX CONCURRENTLY` and batched backfills (5,000 rows per transaction) with a pause switch.
  1128→
  1129→Release windows: no deploys Saturday 18:00 to Sunday 14:00 tenant-local. That is the product's peak, and a bad deploy then is a visible failure in front of the congregation.
  1130→
  1131→Rollback: redeploy the previous image tag. Migrations are forward-only in production; that is why they must be backward-compatible for one release.
  1132→
  1133→### 7.3 Observability
  1134→
  1135→| Signal | Tool | What it must answer |
  1136→|---|---|---|
  1137→| Structured logs | pino → Better Stack or Datadog | Which tenant, which request, which membership, how long |
  1138→| Traces | OpenTelemetry → Honeycomb or Grafana Tempo | Where a slow check-in or statement run spends time |
  1139→| Errors | Sentry, tagged with tenant and release | New error classes, affected tenants, first-seen |
  1140→| Metrics | Prometheus/Grafana Cloud | RED per route, queue depth, job failures, DB connections, replication lag |
  1141→| Uptime | Synthetic checks per region | Is the public giving page up? Is check-in up on Sunday? |
  1142→| Audit | `audit_log` | Who changed what, in which tenant |
  1143→
  1144→SLOs:
  1145→
  1146→| SLO | Target | Consequence |
  1147→|---|---|---|
  1148→| API availability | 99.9% monthly (43 minutes) | Page on 2% error budget burn in an hour |
  1149→| API p95 latency | < 400 ms | Investigate at 600 ms for 10 minutes |
  1150→| Page p95 (admin list views) | < 1.5 s | Investigate per-route |
  1151→| Check-in write p95, Sunday 08:00–12:00 local | < 250 ms | Highest-priority SLO in the product |
  1152→| Webhook processing p95 | < 60 s | Alert on backlog > 100 |
  1153→| Statement run | Every tenant finished within 24 h of trigger | Alert at 12 h |
  1154→
  1155→Alerts that page a human: SLO burn, database CPU > 80% for 10 minutes, queue depth > 10,000, failed jobs > 50 in 5 minutes, backup failure, certificate expiry < 14 days, Stripe webhook 4xx rate > 1%.
  1156→
  1157→Logging rule: never log email addresses, phone numbers, giving amounts or message bodies. Log ids and hashes. A support engineer with log access should not be able to read the congregation's prayer requests.
  1158→
  1159→### 7.4 Backup, restore and disaster recovery
  1160→
  1161→| Objective | Target | Mechanism |
  1162→|---|---|---|
  1163→| RPO, database | 5 minutes | Continuous WAL archiving / PITR, 7–35 day window |
  1164→| RPO, object storage | 24 hours | Bucket versioning, 30-day noncurrent retention |
  1165→| RTO, database | 1 hour | Managed failover plus restore runbook |
  1166→| RTO, full region loss | 4 hours | Cross-region snapshot copy, infrastructure as code |
  1167→| Nightly logical dump | 35 days retained | `pg_dump` to encrypted object storage, different account |
  1168→| Restore drill | Quarterly | Restore to scratch, run integrity checks, record actual RTO |
  1169→
  1170→Tenant-level recovery is a different problem from disaster recovery. Soft delete covers the common "someone deleted 200 people" case for 30 days. Beyond that: restore the latest snapshot to a scratch database, extract the tenant's rows, and re-insert with conflict handling. Rehearse this once before the first enterprise customer; it is the support scenario that decides whether a church stays.
  1171→
  1172→Integrity checks after restore: row counts per table, `sum(donation_splits) = sum(donations)`, orphan check on every composite FK, and a smoke test that renders a giving statement.
  1173→
  1174→### 7.5 Security operations
  1175→
  1176→- Secrets in a managed secret store, rotated every 90 days; no secrets in the repository or in container images.
  1177→- DB roles: `app_rw` (DML only, no DDL, no `BYPASSRLS`), `app_read` (replica, read-only), `app_migrator` (owner, used only by the migration job).
  1178→- TLS 1.3 in transit; AES-256 at rest from the provider; encrypted, checksummed exports.
  1179→- Dependency scanning in CI, container scanning on build, a high-severity advisory blocks release.
  1180→- Support impersonation is explicit, consented, read-only by default, banner-visible, and logged as `impersonation.start` / `.stop`.
  1181→- No direct production database access for support. If access is unavoidable, break-glass with a second approver and a recorded session.
  1182→- Data subject requests: export is self-service; deletion anonymises the person but retains donation rows with a tombstone, because tax and audit obligations outlive the request. Say this in the privacy policy.
  1183→- Annual penetration test before the 100th customer, and a `security.txt` disclosure channel.

  1185→### 7.6 Infrastructure cost model
  1186→
  1187→Assumptions per church: 700 people records, of which 300 are active and email-reachable; 300 weekly attendance rows; 250 donations/month; 8 emails per active person per month (85% bulk, 15% transactional); 20% SMS adoption at 30 messages/month; 2 GB object storage per year; ~150 MB of database per church at three years.
  1188→

  1190→|---|---|---|---|
  1191→| App compute | 40 | 200 | 1,600 |
  1192→| Worker compute | 25 | 90 | 700 |
  1193→| Managed Postgres (incl. replica at 1k+) | 70 | 650 | 5,000 |
  1194→| Redis (rate limits, cache) | 10 | 40 | 250 |
  1195→| Object storage + CDN egress | 15 | 120 | 900 |
  1196→| Email: Postmark transactional + SES bulk | 50 | 640 | 2,700 |

  1201→| **Per church** | **$3.00** | **$2.30** | **$1.45** |
  1202→
  1203→Read as ranges: $250–400, $2,000–3,000, $12,000–17,000. Email routing rule: magic links, receipts and statements stay on Postmark while transactional volume is under ~1M per month; above that, receipts and statements move to SES and Postmark carries only magic links and password resets. Without that switch the transactional line alone would exceed $4,000/month at 10,000 churches. Inputs verified at access date: Neon Postgres at $0.106 per CU-hour on Launch and $0.222 on Scale, storage $0.35/GB-month ([Neon pricing](https://neon.com/pricing)); Fly.io RAM at about $5/GB per 30 days, volumes $0.15/GB-month, egress $0.02/GB in North America and Europe ([Fly.io pricing](https://fly.io/docs/about/pricing/)); SES at $0.10 per 1,000; Postmark and Twilio as cited above.
  1204→

  1206→
  1207→Two cost cliffs to plan for:
  1208→
  1209→1. **Email volume.** Bulk email is the largest variable line and scales linearly with people, not churches. Route bulk to SES from day one; a Postmark-only design is 10× more expensive at 1,000 churches.
  1210→2. **Database migration time, not query load, forces the cell split.** A 20-minute migration on a database past 1 TB is a production outage. Plan the split at roughly 3,000–5,000 tenants per primary, driven by migration duration and backup/restore time, not by CPU.

  1214→## 8. The eight riskiest technical decisions
  1215→
  1216→| # | Decision | Tradeoff: what you gain / what you lose | Recommendation | Cost to reverse |
  1217→|---|---|---|---|---|
  1218→| 1 | **Tenancy model** — shared + RLS vs schema vs database per tenant | Shared: cheap ops, one migration, weak per-tenant restore. Isolated: strong isolation, brutal migrations | Shared schema + RLS + composite FKs, with a routing seam for cells | 1–3 months at 1,000 tenants |
  1219→| 2 | **Who holds the money** — direct charges vs destination vs separate transfers | Direct: no money transmission, church owns disputes, we earn nothing on gifts. Destination: we can take a cut, we own the risk | Direct charges on Standard accounts; monetise the subscription | High: contracts, donor records, regulator exposure |
  1220→| 3 | **Person vs household as the subject** | Person: correct for divorce, adult children, anonymous gifts. Household: simpler statements for couples | Person is atomic; household is a grouping with `is_statement_unit` | 4–8 weeks plus donor-visible restatement |
  1221→| 4 | **Money model** — editable rows vs append-only ledger with splits | Append-only: audit-proof, complex corrections. Editable: simple, unreconcilable | Append-only, reversals, splits, deferred sum trigger | Reporting rewrite; history cannot be reconstructed |
  1222→| 5 | **Permission enforcement** — app-only vs app + RLS + campus scope | Defence in depth: slower to build, catches mistakes. App-only: fast, one missed `where` from a breach | All three layers, with a CI leak suite | 6–10 weeks to retrofit campus scoping into every query |
  1223→| 6 | **Custom fields** — EAV vs JSONB vs columns per tenant | JSONB: fast reads, weak ad-hoc indexing. EAV: flexible, 40k-row joins per screen | Definitions table + JSONB + optional index table later | 2–4 weeks plus index rebuild |
  1224→| 7 | **Check-in and child safety model** | Strong: pickup codes, guardian checks, custody flags, minimal label data. Weak: faster to ship | Build it in v1; it cannot be retrofitted onto a live Sunday | Cannot be undone; a safety incident is existential |
  1225→| 8 | **Reporting architecture** — live queries vs rollups vs warehouse | Rollups: predictable p95, stale by a day. Live: fresh, collapses under January statements | Rollups from 300 tenants; warehouse only past 10,000 | Re-platforming reports and dashboards |
  1226→
  1227→Notes on the two that are most often got wrong:
  1228→
  1229→**#1 Tenancy.** The mistake is not choosing shared schema; it is choosing it without the exit seam. If ids are sequential, joins cross tenants, and files are stored by unnamespaced key, the first enterprise deal becomes a six-week project with a maintenance window. The seam costs about five days on day one.
  1230→
  1231→**#7 Check-in.** Concretely: a four-digit pickup code issued per child per session and stored hashed; a guardian relationship or an authorised pickup list checked before release; `custody_restricted` flags surfaced as a blocking warning; labels showing first name and code, never a surname, address or allergy detail; a staff override that requires `checkin:override` and writes an audit entry. A church will forgive a missing report. It will not forgive a child released to the wrong adult.

   505→- Caveats (honest):
   506→  1. Approvals queue synthesis: Approval model in schema stores only *resolved* approvals (Task 5 finance writes them on approve/reject). Pending approvals are synthesized at query time from `db.expense where status='pending'` (for finance approvers) and `db.event where status='scheduled'` (for events approvers). Synthesized entries have stable IDs like `synth-expense-<id>` so the UI can route decisions to the underlying module endpoint. Historical resolved approvals visible only when `status=approved` or `status=rejected` is explicitly requested.
   507→  2. Event approval not wired end-to-end: Approving an event in the UI currently calls `/api/tasks/:refId` PATCH with empty body, which returns 200 but doesn't change event status. The events PATCH route at `/api/events/[id]` (Task 4) doesn't support an `{action:'approve'}` flow today. Finance expense approvals DO work end-to-end (routed to `/api/finance/expenses/[id]` PATCH with `{action:'approve'|'reject', comment}` which writes an Approval row + changes expense.status + audits). To fully wire event approvals, the events PATCH route would need an `action:'approve'|'reject'` branch — outside my scope (would modify Task 4's file).
   508→  3. Tasks not assigned to members by memberId: Task schema uses `assigneeId` referencing `User.id`, not `Member.id`. Members cannot be assigned tasks directly — only Users (staff). Consistent with the schema but worth noting.
   509→  4. Search excludes pastoral: Prayer requests and pastoral cases intentionally NOT searched even for pastors. Spec said "skip pastoral in search entirely to avoid leakage." A future enhancement could add a separate `pastoral.search` endpoint with explicit user-consent gating.
   510→  5. Audit export capped at current page (50 rows): CSV export button downloads only the currently-fetched audit entries. For full exports, administrator would need to paginate and export each page. Server-side CSV export (like the finance module has) would be a future enhancement but wasn't in scope per spec ("client-side CSV generation from fetched data (capped)").
   511→  6. Member role sees all tasks (not just own): Matrix gives member `tasks:view` which my API treats as org-wide view. The "self only via scope=self" annotation in the matrix is not enforced server-side because the Task model has no `memberId` field — only `assigneeId` (User.id). Members can see the full task board (read-only, since they have no create/update/delete). If true task privacy is required, the schema would need a `memberId` linkage or the matrix entry should be removed.
   512→  7. Settings/System danger zone is informational only: The "Deactivate my account" button is shown disabled with a "Requires re-authentication" tooltip — actual destructive operations require a separate re-auth flow that doesn't exist yet. The button text communicates the requirement rather than triggering the action.
   513→  8. Branches can only be created (not edited/deleted): Per task scope, only GET + POST are exposed on `/api/settings/branches`. Editing or removing branches would need additional PATCH/DELETE routes (not in scope).
   514→  9. User email is globally unique: Schema marks `User.email` as `@unique` (not composite with organizationId). An email can only belong to one organization across the whole system. For multi-tenant SaaS this is a known limitation noted in the schema header comment.

   257→- Caveats (honest):
   258→  1. Member role restricted instead of "self only" — per the verification expectation "Expect: member and pastor GET /api/finance -> 403", I throw ForbiddenError for member role on all finance GET endpoints. The UI shows a notice card directing the member to contact the finance office. The member role's finance:view permission in the matrix is effectively unused — this seemed safer than exposing aggregate finance data or guessing which donations belong to the member.
   259→  2. Fund balance reconciliation is naive — donations confirmed -> fund.balance += amount; deleted confirmed -> fund.balance -= amount; status/amount change on confirmed -> adjust delta. Fund balances from the seed data are 0 (seed sets balance: 0 for all funds and never updates them), so the overview shows 0 balances for all funds. New donations recorded through the API will increment the balances going forward.
   260→  3. Approval record created only on expense approve/reject — for other "approve"-style operations (none currently exist in finance), no Approval record is created. The Approval model has type: 'expense' etc., so future types (event approval, document approval) would extend the pattern.
   261→  4. Donation/expense DELETE permission gate — per the task spec ("DELETE only if status !== 'confirmed' OR require can('finance','manage')"), I gate DELETE with finance:update (which finance_officer, church_admin, super_admin all have) and check inside: confirmed/approved/paid items require finance:manage. The matrix's finance:delete action is unused (no role has it); I picked update as the closest equivalent that church_admin also has.
   262→  5. Attendance report groupBy limitation — Prisma's SQLite adapter doesn't support _count: { records: true } (relation count) in groupBy, only scalar-field aggregates are allowed. I switched to findMany + in-memory aggregation by serviceId.
